# Execution handoff: add supporting subscriptions when instructed

**Updated:** September 11, 2026

**State:** Definition complete; implementation deferred until the publisher asks to build the subscription option.

Read `docs/PAID_PRODUCT_DEFINITION.md` and `docs/GROWTH_ROADMAP.md`. They supersede the earlier Eagle Gold **The Follow-Up** paid-watch experiment. Do not create three pilot briefings, validate a weekly paid cadence, sell exclusive findings or expand the content schema as a launch dependency.

## Fixed direction

- Yukon reporting is the editorial focus.
- Subscribers support the quality and continued existence of public reporting.
- Findings, source links, corrections and substantive follow-ups remain free to read.
- The first-year aim is $200 a month. Confirm currency and gross/net meaning before promising an income outcome.
- Keep Astro, MDX, plain CSS and the strict publication gates.
- No new backend, CMS, authentication, client framework or reader surveillance.
- All outreach is prepared by agents as complete unsent drafts; the publisher reviews and clicks Send.

## Work to do after a build instruction

1. Inspect the working tree, live site and existing provider/account setup. Preserve unrelated changes and never expose provider secrets in Git.
2. Resolve the actual launch choices: price and currency, recurring interval, recipient account, cancellation/refund policy and whether any optional email is offered. CAD $5 monthly is a proposal only.
3. Verify current Canadian provider pricing and relevant requirements from primary sources. Model gross receipts and direct net receipts separately; show the recurring fee and per-payment costs.
4. Prefer one hosted checkout with customer-managed cancellation and receipts. Use an existing suitable account if available. Explain any material new dependency or recurring cost before it is incurred.
5. Add a static support page, a restrained navigation/support link and accurate funding/privacy terms. Follow the copy direction in the definition; promise only what works.
6. Test successful and failed payments in the provider's test mode, receipt accuracy, renewal configuration, cancellation, refund handling, support contact and exportability. Do not charge a real card just to test.
7. Run `npm run format`, `npm run check`, `npm run build`, `npm run validate:build` and `git diff --check`. Inspect 320px mobile and desktop rendering and external checkout links.
8. Present the concrete page, price, costs, terms, test results and any remaining activation action. Carry out the launch only within the publisher's explicit direction and verify the deployed page.

Do not stop at provider recommendations when implementation has been requested: complete all reversible preparation and testing up to the specific account, cost or activation decision that actually requires the publisher.

## Acceptance criteria

A reader can understand that they are funding public Yukon journalism, see the amount and billing interval before paying, find the terms and contact route, subscribe through a tested service, receive an accurate receipt and cancel without newsroom intervention. The public site and its privacy statements reflect the real integration.

Report changed files, validation, the observed checkout state and any precise remaining user action. Never describe a proposed price, test payment or inactive button as a launched subscription.
